# Frame and temporal GNN on the 2060 (05 models 2 and 3, 2026-09-30)

First full CV of both GNNs, on the workstation's RTX 2060. Same folds, held ball, v1 hand features as globals, and τ rule as `lgbm-held-2026-09-27`. Default params for both (no `--gnn-param` tweaks). Runs: `gnn-frame-2026-09-29-h5` / `-h3` at `774afd2`, `gnn-temporal-2026-09-29-h5` / `-h3` and the two degraded temporal runs at `28f9ebd`. Compared by `evaluation.compare` and `scripts/lead_time.py`; outputs sit in each run folder (`compare*.md`, `lead_time*.md`).

## Bottom line
- **Neither GNN beats LightGBM.** Frame GNN: 0.288 vs 0.296 at H = 5 (1/5 folds), 0.294 vs 0.298 at H = 3 (2/5). Temporal GNN: 0.284 (2/5) and 0.290 (1/5). Both win ROC-AUC on 5/5 folds by a hair (+0.003 to +0.004), which doesn't matter for ranking the rare positives. **LightGBM stays the baseline.**
- **History doesn't help (temporal vs frame, the comparison 05 said matters).** 0.284 vs 0.288 at H = 5 (2/5), 0.290 vs 0.294 at H = 3 (1/5). It isn't better where it was supposed to be either: 2–3 s before a shot it's worse on 0/5 folds at both horizons.
- **Lead time doesn't move.** Median lead at each fold's τ: LightGBM 0.71 s, frame 0.75 s, temporal 0.77 s (H = 5). At a matched ≤ 3 false alarms per match, LightGBM catches 172 shots, the temporal GNN 98 (H = 5).
- **On camera-like errors, the temporal GNN ends where LightGBM does.** Every arm at target: 0.284 → 0.225 (−0.059, 0/5 folds better), against LightGBM's 0.296 → 0.226 (−0.070, sensitivity review). It loses a little less but started lower, so it's no more robust in a way that helps.
- **`id_fragment:2` doesn't touch it:** 0.284 vs 0.284 (+0.001, 2/5). Expected (05): tracks aren't followed across steps, so fragmentation only reaches it through `has_vel`.

## What it means
- **The model isn't what's holding the warning back.** A tree model on hand features, a graph over one frame, and a graph over 2.5 s of frames all land at 0.28–0.30 PR-AUC and a 0.7–0.8 s median lead. So did the v2 attack-building features (lead-time review). When three different models hit the same wall, it's the inputs: from positions alone, most shots aren't visible 2–5 s out. More architecture on the same inputs isn't the next step.
- **Stop GNN work for now.** The 05 ablation arms (`--gnn-layers 0`, `--gnn-globals none`) only say which claim a win supports, and there's no win. Park the node-level "who will shoot" head too; it assumed a GNN would be the model.
- **The losses that are still large are upstream:** stage 8's possession (−0.038) and vision errors (−0.070 combined, homography then ball). Both are bigger than any gap between models here.
- **Performance isn't a reason against a GNN later.** Peak GPU memory 0.8 GB (frame) and 1.2 GB (temporal) in training; prediction runs at tens of thousands of rows a second, against 10 a second live.

## Caveats
- Default hyperparameters only, one seed. The fits stop early (best epoch 1–6 of a 40 cap, patience 4), so there may be some headroom from tuning. But the gap to LightGBM (0.008–0.012) is about the fold-to-fold spread, and the temporal model didn't gain where history should matter, so tuning is unlikely to change the verdict.
- The temporal GNN doesn't link tracks across steps (05), so "history" here is where things were, not who moved where.
- Numbers won't match the M1 bit for bit (torch 2.11+cu128 here, 2.14 on the Mac).
