# 03 — Vision Pipeline

## Goal
Turn broadcast video into game state (02) for each frame.

## Inputs / Outputs
- **In:** video file (mp4), optional team rosters.
- **Out:** `match.parquet`, `objects.parquet`, `frames.parquet`, `players.parquet` in schema v0.6 (02).

## Stages
0. **View gate** — decides per frame whether it's a usable match view, before any GPU work. Broadcasts cut to ads, studio, crowd and close-ups; detection on those wastes time and produces junk.
   - **Grass share:** downscale to 160×90, share of pixels in a green HSV range. Below `min_grass` (~0.3) → `other`. ~1 ms on CPU, every frame.
   - **Pitch check:** when stage 4 runs and finds no pitch → `other`, even if green (close-ups on grass, green ads). What counts as no pitch depends on the backend: for `pnlcalib`, no camera that passes the per-call checks (Pitch calibration → PnLCalib); for `roboflow`, fewer than `min_keypoints` (~4) keypoints.
     The last result holds until stage 4 runs again, so failures on stage 4 frames add up across the frames between them. While `other`, a green frame gets a probe every `keypoints_every` frames (feeds the gate only, no homography), so a view comes back on grass and lines, not grass alone.
   - **Hysteresis:** switch to `other` after `off_after_s` (~0.5 s) of failing frames; back to `match` after `on_after_s` (0.5 s) of passing frames. Causal: uses frames `<= t` only.
     `on_after_s` was 1 s until 2026-10-02. On the bench that wait after every close-up was the largest geometry loss (vb01 10.6% of scored frames in `other`, vb02 6.7%). At 0.5 s: 5.4% / 3.5%, within 2 m +3.8 / +3.0 pt, false live unchanged (0.1 / 0.2 s), and no mark re-enters `match` (`Docs/reviews/pnlcalib-bench-2026-10-02.md`, gate section). 8 close-ups on 2 clips is a small sample, so it doesn't go lower.
   - **While `other`:** stages 1–7 don't run. Game state still gets a `frames` row with `ball_state`, `possession_team`, `ball_carrier_id` and `view_polygon` null (02: can't decide → null), and no `objects` rows.
   - **Back to `match`:** reset the tracker (IDs don't survive a cut). Keep the team assignment fit; refit if the break was longer than `refit_after_s` (~120 s, e.g. half-time). A refit matches its clusters to the old ones by kit color, so `home_cluster` keeps pointing at the same kit.
   - **Replays pass the gate** (grass, valid keypoints) and get tracked as if live. See open questions.
   - Thresholds are config values, tuned on labeled broadcast clips.
1. **Detection** — YOLOv8 fine-tuned on players, goalkeepers, referees, ball. Start from Roboflow's pretrained soccer weights.
2. **Tracking** — ByteTrack (via `supervision`) for stable `object_id`s. People down to `track_min_conf` (~0.1) go to the tracker, whose second pass keeps existing tracks alive on weak detections; the ball and kit-color samples need `min_det_conf` (new tracks need ~0.35, inside supervision). A lost track is dropped after `lost_track_s` (~1 s) of wall time, whatever the frame skip.
3. **Team assignment** — kit color (`KitColorTeams`), not roboflow's SigLIP → UMAP → KMeans: far cheaper, which matters live (09). Goalkeepers go to the team whose outfield players stand nearer on average (x).
   - **Samples:** the torso crop (middle of the box's upper half) of each confident player detection (`min_det_conf`), grass pixels dropped. Fit 2-means (10 restarts, lowest inertia wins) once there are `team_warmup_s` of match view and `team_min_crops` crops.
   - **Feature:** mean CIELAB (L, a, b) of the shirt pixels, in CIELAB units (OpenCV's 8-bit L divided by 2.55), so the 2-means distance is plain color difference (ΔE76). Fixed weights, nothing fitted, so a refit compares its centers with the old ones directly (F4).
   - **Track team:** the majority of every prediction for the track so far (causal; a tie keeps its first prediction). Each confident detection votes, so a track's team can still change after its first few frames.
   - **Why (2026-10-01):** the old feature was mean chroma (a, b) only, with L dropped because lighting split smoke03's 2-means, and the team was fixed by the first 5 votes. It fails when kits differ mainly in lightness: vb01 (navy France vs white / sky-blue Argentina) scored 52% outfield. Offline test (`scripts/team_crops.py`, the pipeline's own warmup fit, tracks labeled by majority PFF team after removing each frame's affine, 109 tracks): per crop 53% → 97.4% in CIELAB units. Any L weight from 0.1 to 1.0 × OpenCV's L gives 97.1–97.4% (CIELAB is 0.39), and median instead of mean is the same. Dividing each channel by its warmup spread ties on vb01 but fails the synthetic smoke03 case (a few bright yellow crops split off from both kits, 20 of 20 seeds), so it was dropped. Track team: first 5 votes 97.0%, running majority 97.6%; with the spread scaling the first 5 votes fell to 93.9% while the running majority held, so the running majority is the safer rule (a few tracks start occluded). smoke03 (red vs blue, no truth) splits cleanly by eye. SigLIP (GPU) only if the benchmark clips fall short of the > 95% target.
4. **Pitch calibration** — PnLCalib (a SoccerNet camera calibration model) every `keypoints_every` frames → a full camera → its ground-plane homography → pixel to meters. Calls are accepted, held and smoothed as in Pitch calibration below. Built 2026-10-02 (`vision/calib.py`, `PnLCalibCamera`, `--calib-backend pnlcalib`); it passed the bench and is the default (`Docs/reviews/pnlcalib-bench-2026-10-02.md`: 90.0% within 2 m pooled, from 22.1%). The old backend, roboflow's 32-keypoint model with a RANSAC homography per call (`calib_backend = "roboflow"`, Pitch calibration → Roboflow keypoints), stays for replaying old runs.
5. **Ball tracking** — dedicated detector at higher input resolution; extrapolate short gaps (≤ `ball_max_gap_s`, 0.5 s) forward and mark `interpolated=True`. `BallTrack` (`vision/ball.py`) picks the ball from the frame's candidates and extrapolates; replay uses the same class (Diagnostics → `balls.parquet`).
   - **Built 2026-10-05** (`Docs/Specs/10-ball.md` §2, `Docs/reviews/ball-fix-2026-10-05.md` Phase C), the default for new runs:
     - a gate on the predicted pitch position instead of the most confident candidate (`ball_picker = "gate"`), with reacquisition at confidence ≥ 0.5;
     - candidate filters for size and for distance off the pitch (specks, board logos, the net);
     - a jump faster than 40 m/s keeps its position with zero velocity;
     - extrapolation for at most 0.5 s (was 1 s): with the gate, 1 s of extrapolation cost 2 pt of precision on aerial frames;
     - resets on segments, invalid geometry and a detection without a pitch position; a period change resets by construction (one run is one period).
   - **Still planned:** the ball held at the carrier's feet through short gaps; a reset on confirmed cuts (W3); a fine-tuned ball model from PFF-agreement auto-labels.
   - **Why:** the research review (`Docs/reviews/ball-research-2026-10-02.md`) found the detector is the limit (a candidate near the ball on ~70% of PFF-VISIBLE frames), the picker is worth 1–3 pt, and a larger input under 1 pt. On the verified labels the built rules took pooled recall from 78.8% to 81.1% and precision from 81.4% to 83.1%.
   - Runs before the new fields replay as `"max"` with no filters and any speed (`replay.run_config`), so they reproduce their caches; their own `ball_max_gap_s` (1 s) is in their `run.json`.
6. **Jersey OCR** — read numbers over multiple frames, vote per track, link to roster → `player_id`. Borrow approach from sn-gamestate.
7. **Velocities** — backward differences on trailing-smoothed positions (causal, frames `<= t` only; see 02 `vx, vy`). A centered window would leak future frames into the features.
8. **Game state inference** — fills `possession_team`, `ball_carrier_id`, `ball_state` and `view_polygon` (02). Works on pitch coordinates only, not pixels, so the same code runs on dataset tracking for testing.
   - **Ball carrier:** the player nearest the ball, within ~1.5 m, with ball height < ~1 m where known, for at least ~3 consecutive frames at 10 Hz. Otherwise null (loose ball, pass in flight).
   - **Possession team:** the carrier's team. It persists through passes and loose balls until a player from the other team becomes carrier. Null at the start of a period until someone first controls the ball.
   - **Ball state:** dead when the ball is past a touchline or goal line; dead while the ball is stationary at a restart spot (corner arc, penalty spot, touchline) with players set up; null when the ball hasn't been seen for > 2 s or there is no valid homography (replays, close-ups); otherwise alive.
   - **View polygon:** the four image corners projected through the frame's homography.
   - All thresholds are config values, tuned on dataset tracking (see acceptance criteria).
   - **Implementation** (`vision/state.py`, 2026-09-29). Everything above as one causal state machine, frame by frame: a frame's output uses that frame and earlier ones only, so it runs live and on dataset tracking alike. Thresholds are in seconds and meters, never frames, so any frame rate works. On dataset tracking it reads what vision would see: VISIBLE ball and VISIBLE players and goalkeepers (referees never), so PFF's ESTIMATED positions (later frames, 05 Leakage) never reach it.
     - **Candidate:** the nearest player to the ball on the frame, if within `carrier_radius_m` (1.5) and the ball's `z` is null or under `carrier_max_z_m` (1.0).
     - **Carrier:** a candidate becomes carrier after `carrier_min_s` (0.3) as the candidate. The streak survives frames without a visible ball for up to `carrier_gap_s` (0.5), and the carrier is held through them. It ends when another player or nobody is the candidate on a frame with a ball.
     - **Possession:** the team of the latest carrier. A carrier with no team (vision's unknown) doesn't change it. Reset to null at each period's start.
     - **Team near (`team_near_s`, off by default):** when set, the candidate's *team* being the same for `team_near_s` moves possession too, whichever of its players is nearest, with no carrier needed. The streak ends on a frame with a ball where the candidate is the other team, nobody, or a player with no team, and after a ball gap longer than `carrier_gap_s`. Off is `None`, which `StateConfig.to_dict()` leaves out, so the default config key (05 Caches) and earlier runs' `state_config` are unchanged.
     - **Ball state,** in order: null until the first visible ball of the period, or once the ball has been unseen for more than `ball_lost_s` (2); **dead** once the ball is out (more than `out_margin_m` (0) past a touchline or goal line; a ball that's out has no carrier); **dead** once the ball has been still (speed under `still_speed` 0.5 m/s) for `still_spot_s` (1) at a restart spot (within 2 m of a corner, the center spot or a penalty spot, or inside a goal area), or for `still_any_s` (1) anywhere outside the penalty areas (free kicks; inside them it's usually a keeper holding the ball, which is alive). Dead holds until the ball is in and moving at `kick_speed` (3 m/s) or more, which starts play again. Otherwise alive. **Known limit, after a goal (2026-10-05):** the ball in the net is usually not detected, so no sighting crosses the goal line and the state holds alive until `ball_lost_s` or the camera cuts away; false detections in the goal area can keep it alive longer. A goal-mouth rule (past the line between the posts, dead until a center-spot kick) was measured on the 64 PFF games and rejected: at a 10 s hold it gains 1,219 dead frames and loses 725 alive ones, and it can't fire when vision misses the ball (`Docs/reviews/ball-fix-2026-10-05.md`, Phase E). The fix is on the detector side (10-ball §3).
     - Ball speed is over the last `speed_window_s` (0.2) of visible sightings.
     - The defaults above were tuned on 8 PFF games (`Docs/reviews/stage8-2026-09-29.md`, which has the first values). Two dead-ball possession rules (out → the other team, possession frozen while dead) were tried and dropped: both made agreement with PFF worse.
     - **Result on all 64 PFF games:** possession agrees on 77.9% of frames (82.9% alive), under the 90% target; a confirmed carrier's team agrees 97.9% of the time, but only 26% of alive frames have one. Dead frames come out dead or null 89.9% of the time, but only 6.7% dead (most have no ball in the data); alive frames come out alive 81.0%. Whether that's good enough is decided by 07 #6, not the target: **it isn't yet** (2026-09-29). The same LightGBM on stage 8's possession loses 0.038 PR-AUC (5/5 folds). It collapses on the 14% of rows where stage 8 names the other team, where shots follow PFF's team about 3× as often as stage 8's, and it's a little worse where they agree too (`Docs/reviews/possession-inferred-2026-09-29.md`). Giving the model stage 8's carrier age, or making possession unknown past 10 s without a carrier, recovers none of it (`Docs/reviews/possession-stale-2026-09-29.md`), so the rules themselves change next. 85% of the disagreeing rows are PFF changing possession while stage 8 hasn't followed. Disagreement is 55.6% in the first second after PFF's change, and 30.5% of rows with no visible ball vs 8.7% with one.
   - **Learned possession (proposed 2026-09-30, not built).** This replaces the short draft. Strict nested training is required from the first run; plain out-of-fold training of the outer training matches is not an option. Spec reviewed and revised 2026-09-30 (`Docs/reviews/learned-possession-spec-review-2026-09-30.md`). No schema change: possession still uses 02's `possession_team`; carrier and ball state use their existing fields. Features, probabilities and fit provenance below are internal caches, not additions to schema 0.6.

     **Why this model.** Faster proximity rules (`carrier_min_s = 0.1`, `team_near_s = 0.05 / 0.1 / 0.2`) failed the scored-row bar. They cut first-3-s disagreement by about 15% but doubled positive-row disagreement from 7.8% to about 15% by following defenders' brief touches. Hand rules on proximity stop here. Team shape and motion over the last second may distinguish a turnover from a touch; that is the hypothesis, not an established result. The default rule costs −0.038 PR-AUC at H = 5, worse on 5/5 folds (07 #6). Carrier age and unknown possession past 10 s recovered nothing. See the stage 8, inferred-possession and stale-possession reviews dated 2026-09-29.

Separate unknown height from known low height. An elevated ball is evidence for flight; distance alone does not prove flight.

     - **Hypothesis check, before any fit** (needs the extractor, not a model). The fast rules failed on something the residual doesn't cover: extra errors on positives, well after PFF's change, with the ball visible (stage 8 review, "The change-lag rules on scored rows"). The model only helps if its inputs separate a defender's touch from a real turnover at the moment the fast rule has to decide. Both groups share the same trigger, so only the outcome differs:
       - **Trigger:** every H = 5 scored row where `team_near_s = 0.05` switches to the other team and the default rule doesn't.
       - **turnover** if PFF names the new team within the next 3 s; **touch** if PFF keeps the old team for all of those 3 s; other rows are left out. PFF's later labels only sort the groups and are never inputs.
       - At the trigger row, compute every current-block feature as the extractor defines it, with team codes oriented to the new team (so both groups ask "does the team the fast rule picked look like it has the ball?"). Report the medians, IQRs and a single-feature separation AUC, `max(AUC, 1 − AUC)`, with the group sizes. Also give these on positives only.
       - **Bar:** at least one shape, contact or heading feature at AUC ≥ **0.70**, a separation a tree ensemble can build on without a fit. If none reaches it, stop and return to spec review before any fit: the model's main premise doesn't hold where it matters. The bar uses all trigger rows; the positives view is descriptive. The check reads rule outputs and PFF possession, never shot metrics.

     **Model and label.** One LightGBM binary classifier, raw output `q = P(home has the ball)`, per valid 10 Hz grid row. The emitted probability `p` is symmetrized below. Train on PFF `possession_team`: home = 1, away = 0. Select rows whose PFF `ball_state` is alive, possession is home/away, and `all_estimated` is false. `all_estimated` has 05's exact meaning: no player/keeper has visible true, irrespective of team or finite coordinates. Vision derives it from native objects; a parity check must match the resampler. Keep set plays; do not use shot masks or a shot horizon to choose possession training rows. Give each original row weight 1; its mirror also has weight 1. No class weights or match balancing.
     - PFF `ball_state` only selects training rows. Neither it, PFF possession, carrier, set-play flags, events, shot labels, match ID nor period number enters the feature matrix. Match and period identify boundaries and joins only; attacking direction normalizes coordinates.
     - PFF's own lag is learned too. That is accepted because the downstream labels and 07 #6's scoring use PFF possession. Agreement measures reproduction of that convention, not exact physical control. PFF's lag still caps what the comparison can establish about live accuracy.
     - Copy the fixed baseline values from `prediction/lgbm.py` into the vision implementation; do not import prediction: binary objective/log loss, learning rate 0.05, 31 leaves, minimum 500 rows per leaf, feature fraction 0.8, bagging fraction 0.8 every round, L2 1, max bin 255, deterministic true, force column-wise true, verbosity −1, seed 20260927. Workstation CPU (i5-11400F), `num_threads = 6`, its physical cores, fixed for timing and reproduction (the baseline sets no thread count; a fixed one keeps `deterministic` reproducible). No parameter search. The correlated 10 Hz rows justify the same conservative leaves as the baseline.
     - At most 2,000 rounds, stop after 100 rounds without validation log-loss improvement. For each allowed training-match set T, sort its match IDs, select `round(0.15 * len(T))` with NumPy `default_rng(20260927).choice(..., replace=False)`, and hold those whole matches out for early stopping. This is the baseline's procedure, independent of shots. Mirror after splitting, so both copies stay together. Refit on all T for `max(1, best_iteration)` rounds. Store the probe's training/validation IDs and refit's IDs. Abort if either side has no eligible rows. A “fit” below means this probe plus refit. The early-stopping draw, the probe and the refit depend only on the sorted training-match set T, so two fits with the same T produce the same booster (checked by the determinism test below).
     - Early stopping watches the raw `q` on the held-out matches (original and mirrored rows), while the emitted output is the symmetrized `p` below. That's intended: `p` is a fixed function of the same booster, so it adds no choice to make on validation data.

     **Time and visibility contract.** Feature extraction reads schema 02 native frames, sorted by `(period, timestamp_s, frame_id)`. A usable object has `visible = True`, `interpolated = False` and finite x/y. Why exclude interpolated rows: offline stage 5 fills ball gaps using the detection after the gap, which isn't causal, and live extrapolation (09) is a guess, not a sighting. PFF has 0 rows that are both visible and interpolated, so training never sees them and live mustn't either. The 2D rule below reads the same usable objects. Referees never count. Players include `player` and `goalkeeper`; outfield means `player` only. Team is stage 3's home/away/null assignment. `object_id` may link a track or break a distance tie, but is never an input column. `player_id`, provider vx/vy and ball z are never read by this extractor. Provider velocities can include ESTIMATED positions even on a visible row (05 Leakage).
     - The learned path runs a separate copy of the default rule on these usable native objects with every z forced to null and both `team_near_s` and `possession_model` set to None (no recursive learned call). Its rule possession, candidate, carrier and ball state cannot indirectly expose height. The learned switch changes only possession; carrier, ball state and age remain this copy's outputs. The historical rule path, including its height gate, stays unchanged for old runs and the comparator. Call this the **2D rule** below. Never feed learned possession back into the 2D rule.
     - Grid: 05's per-period `t_s = k / 10`, latest native frame at or before t, skip if older than `1.5 / native_fps` seconds; integer microseconds for comparisons. Vision implements this from 02, with parity tests against resampling; it does not import `prediction.resample` or read its attacking coordinates. Prediction supplies/checks only the grid keys at the bridge.
     - A native gap longer than `1.5 / native_fps` starts a new feature-history segment. A skipped grid point also breaks grid history. Reset ball/contact/motion histories at either gap and at period starts; never interpolate across them. The 2D rule retains its existing period reset and ball-gap behavior across missing frames; its possession and carrier age may therefore outlive a feature segment. This is intentional rule state, not a filled position. Never invent intermediate native frames.
     - On missing-object frames, the current player sets are empty. Ball position may be held for at most 1 s, as in 05's held ball; age continues until the feature segment ends. Player positions are never held. No fresh contact is inferred from a held ball.
     - Let `d = +1` when home attacks positive x, else −1. Normalize each period with `X = d*x`, `Y = d*y` (a 180° rotation when d = −1); home attacks +X. Distances are Euclidean pitch meters. For team a, `s_home = +1`, `s_away = −1`. All coordinates below remain in this home frame; “toward own goal” is longitudinal `−s_a * VX`, positive when retreating. This fixes the wording of the earlier draft, which said attacking goal; it carries the same information with the opposite sign.

     **Exact input columns.** Compute the following 53 scalars (feature contract `pfeat-v1`) at each valid grid time t. Missing numeric values are NaN, passed to LightGBM without imputation, scaling or clipping. Team codes are home = +1, away = −1, and 0 for a present object whose team is unknown (numeric, not categorical). An absent value (no rule possession yet, no ball, no candidate, no contact) is NaN, never 0, so "nobody" and "somebody of unknown team" stay apart; unknown teams never happen on PFF but are common live. Flags/counts are unitless. Times are seconds. The model matrix is Float32, in the listed order; probabilities are Float64. No additional columns enter the model.

     | `rule_team`, `rule_carrier_age_s`, `rule_candidate_team` (3) | 2D rule at the selected native frame u. `rule_team` is the rule's possession, NaN while it has none (before the period's first carrier). Candidate is the current candidate within 1.5 m, using the rule's out-of-bounds check and object-ID tie break: its team code, 0 if the candidate's team is unknown, NaN if there's no usable ball on u or no candidate.      Native contact shares: on each native frame, find the nearest of **all** usable players/keepers to the usable ball. No ball/player gives both teams weight 0. Ties within 1e−9 m split weight equally across the distinct tied team values (home, away, unknown); unknown's share is credited to neither. For `r15`, also require minimum distance ≤ 1.5 m. Hold these weights from native time u to `min(next native time, u + 1.5/native_fps, t)`; a missing-ball/player frame contributes zero. Integrate each team's weight over `(max(segment start, t−W), t]`, divide by the duration of that interval, including unknown/unseen time. The window's start usually falls inside the hold interval of the native frame before it; that frame contributes only the part of its interval inside the window. Zero duration gives NaN. This is elapsed-time share, not a count biased by native fps, and uses no frame after t. The 0.5 / 1 s windows capture brief contact versus sustained control.

## Requirements
- Runs on M1 with `--device mps` for short clips; RTX 2060 for full matches.
- Configurable frame skip for detection (tracker fills gaps).
- Stage 0 runs on every frame, including skipped ones, so a cut is caught within `off_after_s`.
- Every stage can cache its output so later stages rerun without redoing detection.

## Streaming API
One stateful object, one frame at a time. Offline is a loop over it, so live (soccer-live-overlay) and offline share code, and every stage is causal by construction.

    pipe = VisionPipeline(config, stages)
    for frame_id, t, image in video:
        vf = pipe.step(frame_id, t, image)      # VisionFrame
        writer.add(vf)                           # game state (02) + caches
    writer.close()

- `VisionFrame`: `frame_id`, `t`, `view` (stage 0), `homography_ok`, `objects` (object_id, class, team, pitch x/y or null, confidence, `tracked_only`, display box), `ball` (same, or null), `view_polygon`.
- Stages are injected (detector, tracker, team assigner, keypoint or camera model), so tests run with fakes and live mode can swap in smaller models.
- Live forms of stages that are batch-style in roboflow/sports:
  - **Teams:** fit on a warmup window (the first `team_warmup_s` of `match` frames), then assign. `team = null` until fitted.
  - **Ball gaps:** extrapolated forward from the last velocity, `interpolated=True`, never filled from later frames. History older than `ball_max_gap_s` is dropped before a new detection uses it (no velocity measured across a gap), and the ball isn't extrapolated while the homography is invalid or after a detection that has no pitch position.
  - **Airborne ball (10-ball 2g):** a detection whose box is at least `ball_air_ratio` (default `inf`, off, until the fine-tune re-derives it; the demo's `air15` variant uses 1.5; old runs `inf`) × the expected width at its ground projection is airborne, and its extrapolated rows inherit the flag; the next detection that isn't clears it. An airborne row is written `visible=False, interpolated=True` with its ground-projected x/y, so features and stage 8 hold the last ground ball instead of a position ~14 m off. The detections cache is unchanged.
  - **`visible`:** detections are visible. A filled-in box (tracker fill or ball extrapolation) that has drifted entirely out of the frame is written `visible=False` (it's already `interpolated=True`, 02).
  - **Homography:** smoothed over a trailing window only, and only across fits that agree with each other (no averaging across a camera cut). With PnLCalib, the nets run on their own worker and the frame loop uses the last accepted camera (Pitch calibration → Speed).

## Pitch calibration
Stage 4 turns an image into a ground-plane homography, pixels → TV-frame meters (+x right on screen, +y toward the far touchline, center origin, 105 × 68; `to_02` then applies the match direction). Two backends, picked by `VisionConfig.calib_backend`. Both end in one homography per accepted call; the across-call filter and the per-position check (Shared, below) are the same for both.

### PnLCalib (`calib_backend = "pnlcalib"`, built 2026-10-02)
**Why.** The roboflow keypoints are the reason geometry fails, not the fit: on vb03 they put box-front points on a mowing stripe and the fit passes its own check while being wrong (vision bench review, clip 3). PnLCalib (github.com/mguti97/PnLCalib, upstream commit `8c87391`) on the same vision foot points and PFF truth, every 5th frame, no gate or filter: within 2 m vb01 81.7%, vb02 91.2%, vb03 84.1%, median 0.45–0.60 m, against 14.8 / 32.5 / 15.8% for the current stage 4. With the WC14 finetune: 82.7 / 92.1 / 91.8%, pooled 89.2% (`Docs/reviews/pnlcalib-2026-10-02.md`, both sections). It replaces the keypoint model; a PTZ solver on top of the roboflow keypoints would be fixing the wrong input.

**Integration: vendored, behind a stage class.**
- Copy the inference path into `vision/pnlcalib/`: the two HRNet definitions (`model/cls_hrnet.py`, `cls_hrnet_l.py`, with their yaml configs), `utils/utils_calib.py`, `utils_heatmap.py`, `utils_optimize.py` and the world-coordinate tables they import. Add upstream's GPL-2.0 `LICENSE` and a README naming the commit. Changes: package-relative imports and dropping plotting imports (matplotlib), nothing else, so a diff against upstream stays readable.
- **Why vendor, not import `../PnLCalib`:** replay reruns PnLCalib's voting on CPU (Cache, below), so bench numbers depend on that code. In the repo, `run.json`'s git commit pins it. An outside checkout isn't pinned, and the bench couldn't run without it. **Why not call upstream's `inference.inference`:** it reads module globals (`device`, `transform2`), and it thresholds the heatmap peaks before we can cache them. Its 20 lines get rewritten in our wrapper. The calibration size must be the video's frame size, not a hardcoded 1920 × 1080; the bench videos are 1080p, so today's numbers aren't affected.
- `vision/stages.py`: `PnLCalibCamera(weights_dir, prefix, device, fp16)` next to `YoloKeypoints`. `detect(image) -> CalibPeaks` resizes to 960 × 540, runs both nets and takes the max-pool peak per channel: 57 keypoints and 23 lines × 2 ends, each x, y, score in net pixels. GPU work ends there.
- `vision/calib.py` (CPU, used by the pipeline and replay): `camera_from_peaks(peaks, image_size, config) -> Camera | None` applies `pnl_kp_threshold` / `pnl_line_threshold`, `complete_keypoints`, then `FramebyFrameCalib(iwidth, iheight).heuristic_voting(refine_lines=True)`. That's upstream's `inference(..., pnl_refine=True)`. The same module holds the ground homography and the per-call checks below.
- **Weights:** the WC14 finetune, `SV_FT_WC14_kp` / `SV_FT_WC14_lines` (`pnl_weights = "SV_FT_WC14"`, the prefix). Against the base `SV` it's better on all three clips and cuts vb03's no-fit frames 35 → 3; `SV_FT_TSWC` is worse on vb01/vb02 (review). 265 MB each, outside git, in `--pnl-weights-dir` (default: `--weights-dir`, roboflow's). `run.json` `weights` hashes the files stage 4 actually loads, by name. Today's `*.pt` glob would skip them, since PnLCalib's files have no extension.
- **Dependencies:** `shapely` (imported by `utils_optimize`) goes into the `vision` extra, and `scipy` gets a direct pin, since `least_squares` is now in our code path. lsq-ellipse is only used by upstream's training and evaluation code, so it stays out unless a vendored import proves otherwise.

**Output per call: the full camera.** `Camera`: fx, fy, principal point, position (x, y, z), rotation (3 × 3), reprojection error (px), voting mode, and the keypoint and line counts after thresholds.
- Keep it whole. A ball in the air isn't on the ground plane, so placing it later (stage 5, height) needs the camera ray, not a homography. The per-call checks below also use camera parameters.
- Pixel → pitch for people stays a ground homography: `H = inv(P[:, [0, 1, 3]])`, where `P` is upstream's `projection_from_cam_params`. In PnLCalib's world it gives centered meters with y toward the near touchline, so the TV frame is (x, −y). That holds on all three bench clips. Its z points down (the crossbar is at z = −2.44), so camera height is −z.

**Cadence and the view gate.**
- **Keep `keypoints_every` (5) as stage 4's cadence for both backends.** It's one call that feeds both the gate and the camera, as the probe in `other` already does. Old runs keep their field. Decoupling the two only buys anything live, and live needs a lower rate anyway (Speed).
- **Gate signal for `pnlcalib`:** a call passes when it returns a camera that passes the per-call checks. `min_keypoints` and `min_keypoint_conf` become roboflow-only. With WC14 (review): a camera on 1 of 98 sampled close-up frames (vb01 1 / 70, vb02 0 / 28) and 928 of 930 wide frames. The roboflow count drops to 0–3 on 5 s of vb01's wide play (78–83 s) and sends the gate to `other`. PnLCalib has a camera on every one of those frames. The one close-up camera is a single frame, which the gate's `on_after_s` (1 s) absorbs.

**No camera on a call: hold the last one.** A call with no camera, or one that fails the checks, leaves the camera in use until it's older than `homography_max_age_s` (1 s, unchanged). That's the existing filter behavior. **Except a call that sees no pitch:** a rejected call with fewer than `pnl_blind_kp` (4) keypoints drops the camera at once. Close-ups have 0 keypoints on 97 of 98 sampled frames; a broken camera has 4–9, and stays held. Added on the bench: without it, the held camera gave close-up boxes positions through the gate's 0.5 s lag, and false live rose to 2.6 s on vb01 (bench review). With it, 0.1 s.
- **The gate is stricter than the hold.** A rejected call is also a gate failure, and the gate switches to `other` once failures have lasted `off_after_s` (0.5 s, `>=`). So the hold covers runs shorter than 0.5 s; a longer run costs the run plus `on_after_s` (1 s) and a tracker reset. Kept that way so close-up cuts stay out. On the bench vb03's rejected calls at 276–283 s never dropped the view.
- **Why that's enough** (review, last section): with WC14, vb01 and vb02 have no no-fit calls and vb03 has 3 of 360, one 0.4 s run. A 1 s hold gives vb03 92.5% within 2 m, the same as a low-threshold retry (92.6%). The 3–5 s runs in the first PnLCalib look were the base weights on vb03 (35 frames) and, on vb01/vb02, the vision run's own gate dropping to `other`, not PnLCalib.
- **Not done:** falling back to the roboflow fit (worst of the options on vb03, and a second model on the GPU); interpolating between calls (needs the next call, not causal); a longer hold (5 s drifts in a pan: p90 0.98 → 1.48 m on base vb03); a retry at lower thresholds (no gain with WC14; with the base weights the retried fits were 45% within 2 m). Lower thresholds stay available as a replay sweep (`--revote`).

**Per-call checks** (replace roboflow's per-fit checks). A call is rejected, and stage 0 sees a failure, when:
- PnLCalib returns no camera;
- the reprojection error isn't finite or is above `max_calib_err_px`. Upstream's voting keeps a result whose error is NaN (`if ret:`), so this has to be checked here;
- the camera height (−z) is outside `camera_min_height_m`–`camera_max_height_m` (start at 5–60 m), or the camera isn't behind the near touchline (PnLCalib's y ≤ 34 m, i.e. on or over the pitch).

Starting values from the review's WC14 runs on wide play: error p95 4.8–5.5 px at 1920 × 1080, height 13.5–23.9 m, 67–113 m behind the center spot. `max_calib_err_px` starts at 10. These bounds catch broken cameras (below ground, inside the pitch, a reverse angle from the far side), not a good camera that's slightly off; they're guesses to look at on the bench, not tuned. **They're needed:** WC14's voting returns a broken camera on 14 of 360 vb03 frames (focal 0 or 23,746 px, height 0 or 67 m, error up to 186 px, mostly 276–283 s). The bounds reject all 14 and no wide frame on vb01/vb02 (max error 5.0 px). `pnl_compare` scored those 14 as fits, so its vb03 number already pays for them as misses.

**Filtering.** Accepted cameras go to `HomographyFilter` as ground homographies (Shared, below). Average homographies, not camera parameters: positions are what get used, and averaging rotations and focal lengths isn't linear. The jump check moves from the fit's inlier keypoints, which a camera doesn't have, to a fixed grid of image points: 5 × 3 points over the lower two thirds of the frame, keeping those the new homography puts within `max_off_pitch_m` of the pitch. The camera becomes a `Fit` whose src/dst are those pixels and their pitch positions, so `HomographyFilter` itself is unchanged. **`homography_window` 1** (no averaging) and **`max_homography_jump_m` 10**, from 07's sweep: a window of 3 lags every pan, vb01's median 1.09 → 0.70 m with 1.
- **Per-match camera position (PTZ):** the main camera doesn't move during a match, so a call whose position is far from the running median of accepted positions is suspect. Not in v1. The cache records every position, so the bench review can look at the spread first. Add it only if accepted bad calls show up.

**Speed** (RTX 2060, `Docs/reviews/pnlcalib-2026-10-02.md`): ~420 ms a call end to end, nets 305 ms fp32 / 185 ms fp16 autocast, voting and refinement ~60 ms CPU, peak GPU memory 1.9 GB.
- **Offline:** every 5th frame adds ~85 ms a frame on average, so the pipeline goes from ~0.25 to ~0.33 s a frame (4.0 → ~3 fps). fp16 brings that to ~+50 ms. It's a config flag (`pnl_fp16`), off until the bench shows it costs nothing on within 2 m.
- **Live (09):** every 5th frame at 30 fps is 6 calls a second, ~1.5 s of GPU a second even in fp16. Not possible. Holding the camera between sparser calls costs a lot (bench review, replay with every k-th call): every 10th frame 86.4%, 15th 80.4%, 30th 65.8% within 2 m, against 90.0%. So live needs ~3 calls a second or more on their own worker, plus something that carries the camera between calls (frame-to-frame pitch tracking, or a PTZ model). That's still ≥ 0.5 s of GPU a second in plain fp16, so TensorRT or a smaller input too (nets trained at 960 × 540; untested).

### Shared: across calls and per position
The first 2060 smoke test (`Docs/reviews/smoke-test-2026-09-27.md`) put objects more than 15 m off the pitch. When geometry can't be trusted, positions go null. They are never clamped or guessed. All thresholds are in `VisionConfig`, and they are guesses until they're tuned on real clips.
- **Across calls:** a new homography is compared with the one in use: at the new fit's inlier keypoints (roboflow) or at the image grid (PnLCalib, above). If the mean distance is ≤ `max_homography_jump_m`, it joins the trailing average of `homography_window`. If not, it waits and the homography isn't ok until the next call. If that next one agrees with the waiting one, the camera changed and the two start a new window. If it agrees with the old one, the waiting one is dropped. Once the one in use is older than `homography_max_age_s`, any call that passes the per-call checks is taken. Frames already emitted are never rewritten.
- **Per position:** a projection more than `max_off_pitch_m` (10 m, under the validator's 15) outside the lines, or not finite, gets null x/y. The detections cache keeps the row, with `homography_ok` true and a null `pitch_x`. An extrapolated ball that crosses that bound is dropped, and its motion is forgotten. Genuine out-of-play balls within the margin are kept for stage 8.

### Roboflow keypoints (`calib_backend = "roboflow"`, old runs)
Kept so old runs replay and the bench can score both backends. Not developed further.

The keypoint model is roboflow/sports' `football-pitch-detection` (32 keypoints). Its template (`SoccerPitchConfiguration`) is 120 × 70 m in centimetres, origin at a corner, y growing toward the near touchline, with a 20.15 m deep penalty box. We keep its **keypoint order** (that's what the weights predict) but put each landmark at its **real** position in 02's frame (except 31/32, below): meters, center origin, 105 × 68, penalty area 16.5 × 40.32, goal area 5.5 × 18.32, penalty spot 11, center circle 9.15. The homography then outputs 02 coordinates directly, nothing gets rescaled.
- Keypoint 1 (roboflow `(0, 0)`) is the far-left corner as seen on TV → `(-52.5, 34)` in the TV frame.
- Keypoints 9 / 22 (penalty spots) → `(∓41.5, 0)`; 31 / 32 ("circle left / right of the centre spot") → `(∓circle_kp_x_m, 0)`, default **7.2 m**.
  - **31/32 sit where the model puts them, not at the real circle edge (9.15 m).** On vb01 (`scripts/keypoint_check.py`) they land at about ±7.2 m; on vb02 at about −8.0 / +7.5 m. The bench is best at 7.0–7.2 on both (vb01 14.0% → 20.9%, vb02 25.3% → 32.4% within 2 m). On vb03 one side lands near 9.15 and 7.2 barely matters (15.0% → 15.3%): a model bias that varies by stadium, which is part of why the model is replaced. `Docs/reviews/vision-bench-2026-10-01.md`.
  - It's in `run.json` with the rest of the config, so the replay check holds and `--grid circle_kp_x_m=9.15,7.2` scores both. A `run.json` without the field ran on 9.15 (runs before 2026-10-01). It goes away with this backend.
- Keypoints below `min_keypoint_conf` are dropped; at least 4 are needed for a homography (stage 0 counts them against `min_keypoints`).
- **Per fit:** RANSAC at `ransac_m` on the template. A fit needs `min_inliers` inliers and a mean inlier reprojection error ≤ `max_homography_err_m`. Stage 0 still gets the count of confident keypoints, not inliers. Four inliers always fit exactly (error 0), so the across-call check is what catches a bad four-point fit.

## Teams and direction
Clustering gives cluster 0 / 1, and the homography gives the TV frame. 02 needs `team` as home/away and +x toward the goal home attacks in period 1. Two config inputs:
- `home_cluster`: which cluster is home (picked from sample crops at warmup, or a flag). Until set, `team = null`. Never guessed.
- `home_attacks_tv_right_p1`: if false, positions are rotated 180° (x → -x, y → -y) for the whole match, so +x is always home's period-1 attack. `home_attacks_positive_x` is true in odd periods, false in even ones.
- Later: infer direction from which end each team's goalkeeper stands at during warmup.
- `period` and the period start come from config too (live: set at kickoff and half-time).

## Display output (pixel exception)
Pixels never leave `vision/` as data, but the live overlay draws rings on the video, so it needs screen positions. The one exception: `VisionFrame` carries each object's box as fractions (0–1) of the frame, for **display only**. Same status as the detections cache below, which 08's debug mode draws from. Game state, prediction and evaluation never read it.

## Diagnostics
Debugging works from cached data after the run, not from extra logging during it. Nothing here adds work to the inference loop beyond writing the cache.

### Detections cache

|---|---|---|

| x1, y1, x2, y2 | float | Box in pixels |
| det_confidence | float | Detector score; null for tracker-filled frames |
| tracked_only | bool | True if the tracker filled this frame, no detection |
| pitch_x, pitch_y | float/null | Box anchor through the homography; null without a valid homography |
| homography_ok | bool | Per frame (repeated on each row) |

| Column | Type | Notes |
|---|---|---|
| match_id, frame_id | | |
| x1, y1, x2, y2 | float | Box in pixels |
| det_confidence | float | Ball model score |

A detection frame with no candidates has no rows. Which frames ran the detector follows from `view` and `detect_every` (every `detect_every`-th match frame, counted from the switch to `match`), so it isn't stored.

`python -m vision.replay` reruns stage 4's acceptance and the projection from this cache and the detections cache under other `VisionConfig` values. With the run's own config, it reproduces `homography_ok` and the people's `pitch_x`/`pitch_y` exactly.
- **The ball:** stage 5's logic is one class, `BallTrack` (`vision/ball.py`), that the pipeline and replay share. With `balls.parquet`, replay reruns stage 5 from the candidates and the replayed homographies, extrapolated rows included, and with the run's config it reproduces the run's ball rows exactly (the bench's replay check covers them). Runs without `balls.parquet` (before 2026-10-02) keep the old behavior: detected ball rows are reprojected, extrapolated ones dropped, and the bench scores no ball on them.
- **PnLCalib runs:** by default replay reads the cached cameras and redoes the per-call checks, the hold, the filter and the projection. That's what the bench's replay check uses, so it's exact without depending on voting's numerics. `--revote` recomputes the cameras from the cached peaks first (~60 ms a call on CPU, ~30 s a clip), so `pnl_kp_threshold` / `pnl_line_threshold` become sweepable. The implementation checks that `--revote` at the run's thresholds reproduces the cached cameras (bit for bit on the same machine). If it doesn't, `--revote` stays a sweep tool and is reported as such; the replay check never depends on it.
- **Sparser cadence:** a `keypoints_every` that's a multiple of the run's uses every k-th cached call, so the cost of calibrating less often (live, Speed above) can be measured. The gate still saw every call of the run, so `view` stays the run's; it's an approximation and says so.
- **Old runs:** a `run.json` without `calib_backend` is roboflow and replays from `keypoints.parquet` (`replay.run_config` sets the default, as for `circle_kp_x_m`).

Plus `run.json` next to it: config, git commit, model weights hash (each file stage 1–5 loads, by name), video file hash, per-stage wall time, and the 02 validator errors (`vision.run` exits nonzero if there are any; a clip with no match view fails). With the video, this is enough to redraw any moment of the run.

- Anomaly checks (ID switches, ball gaps, homography jumps, ...) are scripts over this cache, written when a real problem shows up. Not part of the pipeline. So far: `python -m vision.offpitch --match-id <id>` (off-pitch rows grouped into runs, with view and keypoint context, plus the count of projections the pipeline rejected).
- The overlay renderer's debug mode (08) draws boxes, IDs and teams for a frame range from this cache.

## Acceptance criteria
- Output passes the schema validator in `tests/`.
- On SoccerNet-GSR validation clips: positions within ~2 m for most visible players (measure with sn-trackeval GS-HOTA as a secondary metric).
- Team assignment correct on > 95% of player-frames on sample clips.
- Stage 8, run on PFF, SkillCorner and IDSSE tracking and compared to provider values: possession team matches on ≥ 90% of frames where the provider has a value; frames the provider marks dead are labeled dead or null ≥ 90% of the time. Starting targets; revisit after the first run. First run (PFF, 2026-09-29): 77.9% and 89.9%, and the dead-or-null share is nearly all null, so it's read with dead → dead and alive → alive beside it (Stage 8 above).
